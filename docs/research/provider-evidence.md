# Reference extraction providers and evidence normalization

Research for [Research reference extraction providers and evidence normalization](https://github.com/vineetsarpal/re-ink/issues/46), 2026-10-14. Scope: implementation-ready specification, synthetic-document demo first, explicit customer deployment path. These are options for a later human decision, not an implementation or provider selection. No credentials were inspected, no provider calls made, and no accuracy, latency, or cost comparison measured.

## Local contract to preserve

Inspection is pinned to repository commit `cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6`:

- The [extraction schema](https://github.com/vineetsarpal/re-ink/blob/cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6/backend/app/schemas/extraction_schema.py) defines contract identifiers, parties, dates, financial as-written text/numeric pairs, coverage and terms. Some descriptions permit inference; a normalized/inferred value must not be presented as a literal quotation.
- The [current LandingAI service](https://github.com/vineetsarpal/re-ink/blob/cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6/backend/app/services/landingai_service.py) calls `client.parse` then `client.extract`, joins extraction references to parse chunk IDs, converts zero-based pages to one-based display pages, strips HTML from source text, and maps schema names such as `premium_text` to display names such as `premium_description`. Unresolved references can yield a page hint; absent references yield no source. It also generates a contract number from the title and defaults currency to USD; these are application derivations, not source evidence.
- [Frontend result types](https://github.com/vineetsarpal/re-ink/blob/cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6/frontend/src/types/index.ts) expose `contract_data`, `parties_data`, optional `field_sources`, confidence and metadata. Sources are keyed by contract display column and party array index. Each field currently has one optional source containing value, text, page, chunk ID, normalized rectangle and confidence. [DocumentPreview](https://github.com/vineetsarpal/re-ink/blob/cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6/frontend/src/components/DocumentPreview.tsx) renders normalized rectangle coordinates as percentages.
- [Source-grounding tests](https://github.com/vineetsarpal/re-ink/blob/cf52e5bb5e1e4ae96cafe092718a0d7cff5f70e6/backend/tests/test_source_grounding.py) explicitly use synthetic fixtures and disclaim verification against a live response. They establish adapter behavior, not live provider compatibility or extraction quality.

## Two materially different live options

### LandingAI ADE: schema-driven parse and extraction

Official SDK documentation supports PDF/image parsing, JSON Schema extraction, and field grounding. Current v2 returns Markdown plus a spatial structure tree, per-field Markdown ranges, and a join back to grounded blocks. Its offsets are Unicode code points and boxes normalized to 0–1. Grounding can be disabled, leaving ranges null; schemas can be checked strictly. Keys are generated in the ADE account and are environment-specific. File upload or document URL supplies the parse input; Markdown and schema supply extraction input. These inputs therefore leave the workflow host for LandingAI. The local adapter uses the older v1 chunk/reference shape: v2 is not a drop-in response replacement. Pin the API/model/adapter version and retain the matching parse/extract pair. These are documented capabilities, not verification on our corpus. [Official LandingAI SDK](https://github.com/landing-ai/ade-typescript#readme).

Feasibility inference: this is the closest option to the existing semantic schema and needs an ADE account/key, approved endpoint access, and response fixtures from the chosen API version. Detailed retention, contractual region commitments and customer entitlement remain unverified here; resolve those before customer deployment rather than inferring them from an SDK environment switch.

### Azure Document Intelligence: trained custom neural fields

Custom neural extraction learns labeled fields from a supplied training set and supports key/value, selection mark and table fields. Microsoft documents a limitation for values split across page boundaries. This differs from supplying a general JSON Schema for each ADE extraction. [Custom neural documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-neural?view=doc-intel-4.0.0). Custom models can start with five examples of the same document type; this is a minimum to start training, not evidence of accuracy or coverage. [Custom model documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/train/custom-model?view=doc-intel-4.0.0).

Layout analysis supplies text, tables, pages, and spans; custom named fields still need training/mapping to the reinsurance schema. Layout/OCR alone is not a full contract extractor. [Layout documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0). Analysis responses include one-based page regions, polygons in page units, and offsets into content. PDF units are normally inches and image units pixels; Office inputs currently lack bounding regions. Character offsets default to grapheme clusters, so do not assume JavaScript UTF-16 indexing. [Analyze-response documentation](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/concept/analyze-document-response?view=doc-intel-4.0.0).

Access needs an Azure subscription, Document Intelligence resource, endpoint and key (or supported Entra configuration); custom training additionally needs labeled synthetic samples and storage access. [SDK/REST prerequisites](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/how-to-guides/use-sdk-rest-api?view=doc-intel-4.0.0). Documents leave the workflow host for Azure; custom training uses customer Azure Blob storage. Microsoft documents temporary input/results storage in the resource region, automatic deletion after 24 hours following completed analysis, and earlier deletion through Delete Analyze Result. Training outputs/models have their own storage lifecycle. [Data privacy and security](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/document-intelligence/data-privacy-security).

Feasibility inference: suitable as the contrasting reference implementation if the human accepts labeling/training work and a bounded synthetic document family. It cannot be represented as ready solely because Azure has OCR. Whether its trained fields cover the complete schema remains a live evaluation question.

## Normalization implications for the specification

The following are proposed design constraints inferred from the local review surface and documented provider differences; they are not decisions already made:

1. Keep provider-specific IDs, raw responses, model/API version and coordinate/offset units in adapter metadata; map output to common contract/party/display keys before review. Use stable document/job identity to prevent joining evidence from another upload.
2. Canonical pages should be one-based. For Azure polygons, divide each x by page width and y by page height, then take min/max to form the existing rectangle. Preserve the original polygon: an axis-aligned rectangle may over-highlight rotated text. Validate finite dimensions and bounds; never guess page dimensions or apply another provider’s page offset. Confirm page numbering for the exact ADE version with its fixtures before reusing the v1 conversion.
3. Preserve source text as a quotation distinct from normalized value and inference. Missing source, page-only source, full visual source, and derived value need distinguishable states. Never manufacture a box or quote to make outputs look equivalent.
4. A field can have several evidence spans/pages. The existing single-source shape returns only the first resolved reference and cannot faithfully represent all such support. Decide whether to extend it to a list or explicitly accept a documented first-source projection; retain all evidence in either case.
5. Confidence is optional and provider-specific. OCR word confidence, field extraction confidence and overall contract correctness are different quantities. Do not synthesize a global comparable score from missing or differently defined values.
6. Both live candidates require external AI approval in customer deployment. Customer-specific n8n routing alone does not keep data local. The specification must identify provider endpoints, storage, workflow execution/log retention and deletion ownership.

## Fixture versus live acceptance

A deterministic adapter fixture can exercise keys, nulls, page-only evidence, multiple references, table cells, rotated polygons, Unicode offsets, and malformed/partial output without credentials. It must be labeled as a fixture; it proves neither a second live integration nor measured extraction accuracy. Live acceptance requires approved credentials, known synthetic documents, captured versioned responses, field/evidence checks against human-authored ground truth, and deliberate missing/ambiguous-field cases. These are evaluation prerequisites, not implementation delivered by this research.

The next human choice is which two live implementations, document formats and synthetic document family to require, including whether Azure training effort belongs in the demo. Exact evidence multiplicity, derived-value policy and confidence semantics remain contract decisions for the map.
