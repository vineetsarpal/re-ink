# Simulated customer environment: VPS runtime

The VPS runs n8n, an HTTPS proxy and the dispatcher. The existing hosted API/frontend and Neon database stay on their existing hosts. Private R2 originals and external providers are separate services. Use synthetic documents; this topology does not establish private networking, document residency or production certification. These templates do not provision resources or certify a live deployment.

## Operator prerequisites and startup

Actual VPS SSH/admin access, DNS, HTTPS, Neon restricted-role connectivity, R2 activation/bucket credentials, provider billing/model access and secure secret injection remain prerequisites.

1. Check out the same backend release as the hosted API. Copy `.env.example` to `.env` and `dispatcher.env.example` to `dispatcher.env`; protect both with mode 0600. Replace placeholders. Expose only HTTPS/HTTP certificate issuance and controlled SSH. Do not publish n8n, worker, database or Docker management ports.
2. Generate a proxy password hash using `caddy hash-password`. The proxy barrier protects the editor and owner setup from the first public start. Create n8n's own administrator immediately after HTTPS starts, configure MFA, and keep the proxy barrier. Only `/webhook/reink-extraction-v1` bypasses proxy authentication; its independent n8n Header Auth credential remains mandatory. Confirm the imported production webhook uses this exact path. Test webhooks stay behind proxy authentication.
3. Create `secrets/n8n_encryption_key` containing a strong random key. Give the n8n container user read access without public access. Preserve this secret and the `n8n_data` volume across restart/restore; overwriting the key makes saved credentials unreadable. Import the sanitized reference workflow **inactive**, bind credentials locally, then publish only after validation. Pin image 2.43.4 and Webhook 2.2, HTTP Request 4.5, Respond 1.5, Wait 1.1. Record the resolved digest, actual `n8n --version` and all node versions after import.
4. Configure the hosted API with `WORKFLOW_CUSTOMER_ORG_ID`, trusted HTTPS `WORKFLOW_WEBHOOK_URL` and distinct random `WORKFLOW_DISPATCH_TOKEN` / `WORKFLOW_SERVICE_TOKEN` (each >=32 characters). Bind dispatch token to incoming n8n Header Auth and service token to its backend Header Auth credential. Machine identity grants claim/document/callback access only; it never grants human approval or publication. Browser resource access is restricted to the configured org. Secrets belong in protected server settings and n8n credential storage, never exports, URLs, Code nodes, browser bundles or chat. Keep `WORKFLOW_UPLOADS_ENABLED=false` until the complete release gates pass.
5. Inject R2 configuration only into API/cleanup: `STORAGE_BACKEND=r2`, `R2_ENDPOINT_URL`, `R2_BUCKET`, `R2_REGION=auto`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`. Use a private dedicated Standard bucket and its bucket-restricted Object Read & Write credential. n8n and dispatcher receive no R2/provider/WorkOS keys. Cleanup runs separately with `python -m app.worker --cleanup`, its own restricted database identity and R2 injection; the dispatcher does not implicitly perform cleanup.
6. Inject a dedicated Neon worker URL with `sslmode=verify-full` into both database URL settings in `dispatcher.env`; the image includes CA trust. Grant only the job/attempt/outbox/receipt/cleanup tables needed by that role, with RLS, no ownership/BYPASSRLS, and no writes to approved contracts/parties. Keep migration credentials separate. The worker rebinds customer scope every transaction and uses short leases and a bounded pool. Prove actual VPS DNS/TCP/TLS/login and a rolled-back scoped lease transaction; verify another tenant and approval writes are denied. Correct configuration if this fails; never weaken TLS or substitute owner credentials.
7. Validate `docker compose config --quiet`, build and run `docker compose up -d --build`. Migrations run through the existing controlled deployment flow before this release. Coordinate the upload pause and old-worker shutdown before cutover. The image starts `python -m app.worker` from the same release.

## Independent rotation

Pause dispatch, replace n8n's incoming Header Auth and API/dispatcher dispatch token, restart the dispatcher and verify new acceptance plus old-token rejection. Separately pause intake, replace the API service token and n8n backend Header Auth credential, restart API and verify new claim/document/callback access plus old-token rejection. Resume after verification. Rejected in-flight callbacks may time out and need manual Retry; do not rerun provider nodes to repair transport ambiguity. Rotate R2 independently in API/cleanup, checking synthetic put/get/delete and old-key denial. Changing the n8n encryption key requires its supported credential migration/restore procedure, not file replacement.

## Retention and reset

Originals/results persist until explicit scoped deletion/reset. Deletion first revokes application access and queues durable object cleanup; failures remain pending. Do not delete unrelated tenants/contracts/parties. Reset must cover both object cleanup and workflow payloads. n8n prunes executions after 168 hours; asynchronous deletion, active/waiting/annotated executions and delete buffers mean this is not exact seven-day physical removal. Verify stranded executions, filesystem binary files, pinned editor data, exports and snapshots during reset. Never pin documents. Successful payload saving is disabled; errors may retain document content and require cleanup.

n8n console logs are discarded because node errors can include payloads. Keep only sanitized backend operational metadata: job/attempt/event IDs, state and safe error code; never document text, prompts, tokens or URL credentials. Before activation configure the host journal (or a dedicated namespace) with `MaxRetentionSec=30day` and bounded size, and verify its effective policy. Docker size rotation alone does not establish thirty-day retention. Proxy access logs are disabled. Record actual Neon restore windows, VPS snapshot policies and manual-backup owners/expiry; source does not establish these. Protect n8n state/key backups with documented expiry. Bucket durability is not an independent backup. Reset discloses retained backup copies.

## Validation, cutover and rollback

The pinned source is reviewed, not runtime certified. Before enabling uploads prove admin/bootstrap protection, independent webhook/service auth, trusted HTTPS/TLS, restricted database permissions, state/credential persistence across restart, duplicate claim fencing, lost acknowledgement, owner crash/timeout, callback replay/conflict/retry/deadline behavior, stale/deleted access rejection and durable physical cleanup. Both provider branches and all six evaluation cases must pass their separate recorded gates. Keep backend deadlines authoritative; n8n's 660-second execution guard is only a resource limit. Record full failures and separate deterministic checks, live interoperability, field correctness and evidence coverage. See `docs/integration/n8n-reliability.md`.

Pause uploads and dispatch before rollback, preserve work/objects, deactivate the workflow and restore the previous tested compatible application/export. Do not drop additive tables/reset state or rerun owned attempts to roll back. Re-enable only a verified compatible path; expired jobs use manual Retry with a new attempt. A successful build alone proves neither live readiness nor exactly-once provider execution.
